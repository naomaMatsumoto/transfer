# 仕様整理：法人・店舗・契約・ログイン

## 1. 用語と関係

| 用語 | 説明 |
|------|------|
| **法人** | 契約の主体。1法人につき1契約。複数店舗を保有できる。 |
| **店舗** | 法人が保有する実店舗。カレンダー・クラス・イベント・会員・スタッフは店舗単位で存在する。 |
| **契約** | 法人ごと。契約に紐づく法人の店舗だけが利用可能。 |
| **アカウント** | 管理画面にログインするユーザー。1つの法人に紐づく。その法人の店舗のみ操作可能。 |
| **会員（users）** | 店舗の顧客。予約・振替・欠席登録を行う。店舗ごとに存在。 |

## 2. ルール

1. **契約は法人ごと**  
   課金・契約単位は法人。1法人 = 1契約。

2. **法人は複数店舗を保有可能**  
   例：法人A → 店舗1, 店舗2, 店舗3。

3. **他の法人の店舗は見えない**  
   ログインしたアカウントの法人に属する店舗のみ表示・操作対象。他法人の店舗・会員・イベントは一切見えない。

4. **店舗ごとにカレンダーの仕様が変わる**  
   表示仕様・営業日・クラス種別・定員などは店舗単位で設定可能（将来の店舗別設定で対応）。

## 3. データのスコープ

- **法人** → 複数の **店舗**
- **店舗** に紐づくデータ：
  - クラス種別（class_types）
  - イベント（events）
  - 会員（users）
  - スタッフ（staff）
  - 振替権利（makeup_credits）
  - 予約（reservations）※ イベント経由で店舗に紐づく
- **アカウント** → 1法人に紐づく → その法人の全店舗のみアクセス可能

## 4. ログイン後の動き

1. アカウントでログイン（メール + パスワードなど）。
2. セッション（または JWT）に「法人ID」を保持。
3. 管理画面の API はすべて「その法人に属する店舗」だけを対象に取得・更新。
4. 会員向けカレンダーは「店舗」または「会員が属する店舗」単位で表示（URL や選択で店舗を識別）。

## 5. フロー

### 5.1 事業者（法人・個人事業主）のフロー

1. **事業者申し込み**（`/corporation/register`）
   - **事業者の種類**で「法人」または「個人事業主」を選択。
   - 法人の場合は法人名、個人事業主の場合は屋号・事業者名、および店舗名・管理者メール・パスワード・表示名を入力。
   - 送信で corporations（organization_type 付き）・店舗・アカウントを1件ずつ作成。
   - 完了後、ログイン画面へ誘導。そのアカウントでログインし、管理画面を利用可能。

### 5.2 会員登録のフロー

1. **会員登録**（`/register` または `/register?store=1`）
   - 店舗を選択（URL に `?store=1` があれば初期選択可）。
   - 名前・メールアドレス（必須）、ふりがな・電話（任意）を入力。
   - 送信で会員（users）を1件作成（email_verified_at は NULL）し、認証用トークンを発行。メール（送信元: support@dynamo-b-studio.com）で認証リンクを送信。
   - 画面上は「登録を受け付けました。メール内のリンクをクリックして登録を完了してください」と表示。
2. **メール認証**（`/register/verify?token=xxx`）
   - 会員がメール内のリンクをクリック。
   - トークンが有効なら `users.email_verified_at` を更新し、トークン削除。「会員登録が完了しました」と表示。カレンダーへ誘導。
   - 無効・期限切れの場合はエラー表示し、会員登録へ戻る案内。

## 6. 実装の段階

| 段階 | 内容 |
|------|------|
| Phase 1 | 法人・店舗・アカウントのテーブル追加。ログイン画面とログイン API。管理画面は「ログイン必須」に。 |
| Phase 1b | 法人申し込みフロー（POST /corporation/register）、会員登録フロー（GET /stores, POST /members/register）。users に store_id 追加。 |
| Phase 2 | 既存テーブルに store_id / corporation_id を追加し、API を法人・店舗でフィルタ。他法人データを返さないようにする。 |
| Phase 3 | 店舗ごとのカレンダー仕様（設定テーブル・店舗別表示の切り替え）を検討・実装。 |

## 7. 運営管理（SaaS プラットフォーム側）

SaaS として販売する際の「運営側」管理画面を簡易実装している。

- **対象**: プラットフォーム運営者（法人・テナントとは別の管理者）。
- **認証**: `platform_admins` テーブル（email / password_hash）。セッションは `req.session.platformAdmin`。
- **画面**: `/ops/login` でログイン → `/ops` で法人一覧。法人ごとに「詳細」で店舗・アカウント一覧を表示し、店舗の追加が可能。
- **API**: `POST /ops/auth/login`, `GET /ops/auth/me`, `POST /ops/auth/logout`。`GET/POST /ops/corporations`, `GET /ops/corporations/:id`, `POST /ops/corporations/:id/stores`（要ログイン）。
- **初回**: 運営管理者は `ops@example.com` / `ops-password` でログイン可能（ensureAuthTables で自動作成）。

このドキュメントは上記仕様に基づき、ログインと法人・店舗の段階的実装の前提として使用する。
